Yeah — **this is cold.** The research has uncovered something much bigger than “dynamic forms.”

What you have here is the beginning of the **deterministic experience projection plane for SideFX**.

The README’s most important conclusion is not that SideFX can render JSON Schema. It is this:

> **A Scenario can carry enough governed authority to deterministically project both the interaction that supplies its Input and the experience that reveals its Outcome — without putting AI in the runtime path.**

And the 824-scenario inventory gives that claim real teeth rather than making it a design fantasy.

# 2. The 239 same-contract scenarios prove why this cannot be “schema → form”

This might be the single most important empirical result.

There are **239 scenarios where Input and Outcome use the same contract**. 

Think about what that destroys immediately:

```text
"This property is in an input schema,
therefore the user should edit it."
```

Nope.

A carrier may contain:

* user-provided facts,
* accumulated evidence,
* existing findings,
* system context,
* derived values,
* terminal values,
* prior state.

The same JSON shape may travel through the circuit.

So the report's five-way ownership model is absolutely foundational:

```text
FIELD OWNERSHIP

human-supplied
system-bound
fixed
derived
unclassified

      +

sensitivity
```

That is **interaction authority**.

JSON Schema can't tell you that.

And now we've got a really elegant architectural separation:

```text
DATA CONTRACT
What values are admissible?

INTERACTION AUTHORITY
Who may supply or change them?

PRESENTATION AUTHORITY
How should people interact with or perceive them?

TARGET REALIZATION
How does React/WPF/etc physically render them?
```

That separation is beautiful.

# 8. The `$id` collision finding is not a footnote — it's a red wall

So:


is dead on arrival.

And:

No guessing.

# 10. One gap I think this research exposes for the architecture

This line is important:

> **Outcome-product / variant-product relationships: 0 / 0.** 

We've been developing:

```text
Outcome
  ↓ realizes
Capability Product
  ↓ becomes consumable Input
```

The database has outcome contracts and variants, but apparently **does not yet carry normalized outcome-product relationships**.

That's not necessary for the first renderer.

But longer term, I think it's the missing semantic bridge for richer result experiences.

Because eventually:

```text
Outcome
"the report is available"
      ↓

Product
ReportArtifact
      ↓

Presentation role
document
      ↓

Target realization
PDF viewer / download / preview
```

is much stronger than:

```text
schema has string property named artifactPath
→ maybe show download button?
```

**Absolutely do not infer the latter.**

So I would keep the first implementation profile-driven, but flag normalized **Outcome → Product → Presentation** as an architectural opportunity.
