# The SideFX scenario experience opportunity

**The opportunity is real: SideFX can make human interaction a reproducible projection of capability authority.** A capability could carry the meaning needed to supply its inputs, invoke its declared behavior, interpret its outcomes, and present those outcomes through compatible UI targets. The research provides a concrete estate, existing presentation vocabulary, and identifiable engineering gaps against which to prove this direction.

The team's review correctly identifies an opportunity broader than dynamic forms. Its central proposal—scenario authority compiled into an experience plan and realized by target providers—is consistent with the inspected architecture. The evidence supports pursuing that architecture. It does not yet establish a universal experience compiler, automatic bespoke UX, or experience parity across targets.

The proposed thesis is:

> A SideFX capability, combined with explicit interaction and presentation authority, can project a reproducible human interface and outcome presentation into a compatible target, with traceable evidence of what was preserved and what remains unsupported.

This is an architectural opportunity and proposed design direction. It is not a capability admission, a new database object definition, or a claim that the proposed compiler is implemented.

## The four-layer model

The review's four-layer model is a sound working separation. The first two layers are complementary authorities. Interaction meaning cannot generally be derived from data admissibility alone.

| Layer | Owns | Does not establish by itself |
|---|---|---|
| Contract authority | Valid data shapes, constraints, alternatives, and references | Who may enter a value, whether an operation may execute, or the intended layout |
| Interaction and experience authority | Field ownership, exposure, semantic roles, state relationships, commit actions, result interpretation, presentation profiles | Successful execution or satisfaction of promised experience conditions |
| Experience plan | A deterministic, traceable compilation of compatible authority into bindings, semantic regions, rules, and coverage obligations | New permission or a change to the source contract |
| Target realization | Concrete components, native wiring, accessibility behavior, and target-specific adaptation | Permission to reinterpret input/output meaning |

```text
Scenario identity and pinned authority
          |
          +-- Input and outcome contracts + scoped resources --+
          +-- Interaction ownership, exposure, and actions -----+
          +-- Presentation meaning and design-system profiles --+
                                                              |
                                                              v
                                                Semantic experience plan
                                                              |
                                     Target binding + compatible providers
                                                              |
                                                              v
                                                    Native interaction
                                                              |
                                            Declared scenario invocation
                                                              |
                                                              v
                                             Admitted outcome + evidence
                                                              |
                                               Bound outcome presentation
```

The experience plan may package input and outcome subplans together. They should retain separate direction-specific bindings and completeness findings. Shared schema resolution does not imply that an outcome is merely an input form with disabled controls.

Compilation should preserve a target-neutral semantic core. A target binding can then select compatible controls, layout behavior, locale, and adapters, producing its own bound-plan identity and findings. Geometry in the core should describe layout obligations and relationships where possible; one universal set of pixel coordinates would not establish equivalent interaction across desktop, browser, and mobile surfaces.

## What a Scenario Experience Plan should mean

“Scenario Experience Plan” is a working architectural name, not an admitted contract ID. Its value is that it makes the relationship between meaning and physical interaction explicit and reviewable.

| Plan area | Minimum retained meaning |
|---|---|
| Identity and provenance | Scenario/version, direction bindings, source contract digests, resource closure, selected profile identities, compiler and registry versions |
| Input | Instance paths, schema locations, ownership, sensitivity, state bindings, labels, required/presence rules, branch behavior, and declared commit actions |
| Outcome | Result-contract identity, variant interpretation, semantic regions, collections, artifacts, findings, evidence references, and empty/absent behavior |
| Presentation | Component roles, ordering/grouping, layout constraints, token references, formatting semantics, and accessibility obligations |
| Coverage | Every applicable path classified as editable, displayed, fixed, system-bound, derived, intentionally omitted, or unsupported |
| Target binding | Provider identities, target profile, adaptations, unsupported obligations, and realization digest |
| Conformance references | Shared vectors and the source obligations against which observed behavior will be assessed |

The plan is derived from authority. It does not become a new source of permission merely because compilation succeeded. For example, a disabled field is only a visual consequence of an ownership rule; the serialization and execution boundaries must enforce that rule as well.

Existing `construct-deterministic-realization-plan`, `construct-consumer-projection-plan`, and presentation-layer contracts already concern planning and projection evidence. Their census entries are relevant integration references, but do not establish that a suitable full experience-plan contract already exists. The first design task is to map required responsibilities onto existing authority, then identify the smallest missing declaration. Adding a parallel planning system before that comparison would create unnecessary competing meaning.

## The product consequence

A capability could become an asset that supplies more of its own invocation experience. A host could discover an exposed root, resolve its compatible authority, bind the user's permitted context, and render an appropriate interaction without hand-authoring the entire page for that capability.

The same retained scenario meaning could support three related projections:

| Projection | Human or system need served | Additional requirements |
|---|---|---|
| Execution | Perform the declared behavior | Executable providers, dependencies, contracts, and runtime evidence |
| Interaction | Supply inputs and understand outcomes | Ownership, presentation profiles, UI providers, context binding, and observed interaction behavior |
| Explanation | Understand the capability, its operation, and evidence | Audience/content authority, explanation format, and supported document/diagram/media providers |

The third projection is a strategic extension, not a result proved by the form census. “Same semantic asset, several projections” is the credible organizing idea. Each projection still needs its own declared obligations and evidence.

The expected benefits are less duplicated interface logic, reusable design-system behavior, clearer impact analysis when contracts change, and a more portable capability catalog. These are hypotheses to measure. Useful measurements include time to add an exposed capability, percentage of fields with explicit ownership, reuse of presentation profiles, unsupported-path rate, target conformance results, and defects caused by contract/UI drift. The research does not yet quantify savings or establish market differentiation.

“Self-interactive capsule” should therefore mean **a capsule that carries or binds sufficient experience authority for a compatible host**. It does not mean the capsule needs no host, that every capability should be exposed, or that a provider connection alone supplies all UX semantics.

## Experience delivery is larger than outcome display

The review is right that outcome presentation makes the intended experience physically accessible. However, a correct view and a fulfilled capability promise are separate claims.

For a provider resolver, displaying an eligibility list faithfully is a presentation obligation. Whether eligibility was established under the required evidence is a domain obligation. For narration, showing a player is a presentation obligation. Whether an admitted, accessible asset contains the promised narration requires separate observations. For authentication, a success panel cannot establish that a session exists.

The existing `prove-experience-closure` declaration evaluates promised conditions from runtime observations, with each condition satisfied, unsatisfied, or not observable. The UI must preserve these states. It cannot turn absent observations into satisfaction, or turn a completed kernel execution into business success. [Source: experience-closure declaration](C:/lab/repos/agentic-harness/features/prove-experience-closure.feature).

Similarly, `prove-cross-apply-ui-parity` describes comparison of digest-bound authority, shared vectors, semantic/presentation testimony, and native wiring across embodiments. It explicitly does not render or wire those embodiments. This supports the review's direction while locating the remaining work: target providers must produce the relevant observations. [Source: UI parity declaration](C:/lab/repos/agentic-harness/features/prove-cross-apply-ui-parity.feature).

The selected input contracts expose fields such as `parityMatches` and `closureStatus`. A generated form must not let an ordinary user supply these assertions as proof. Their origin, measurement, and binding must be established through the appropriate authority. The presence of an assurance-shaped JSON contract is not an independent assurance result.

## Determinism and proof

The deterministic claim should be stated at three boundaries:

| Boundary | Required property |
|---|---|
| Compilation | Identical complete authority, policy, and versioned context produce an identical canonical semantic plan |
| Interaction | The same relevant state and action sequence produce the same declared state transitions and serialized values, within the target's stated support |
| Interpretation | The same admitted outcome and presentation authority produce the same semantic result interpretation |

External operations can still return different results. A lookup can change; a provider can fail; a scenario can intentionally call an LLM. The experience mechanism is deterministic in how it responds to those explicit inputs. It does not make an external service or AI-generated business result deterministic.

Cross-target conformance should compare each target against independently declared obligations and vectors, not merely compare two outputs derived from the same potentially defective compiler. Matching bugs are not preserved meaning. The existing [cross-target embodiment investigation](../../cross-target-embodiment.md) makes the same distinction between agreement with a selected provider and conformance to declared meaning.

The first proof should establish input serialization, validation behavior, presence states, ownership, branch transitions, result interpretation, native wiring, and accessibility observations. Later targets should preserve those semantics while recording justified adaptations. “Experience parity” must be decomposed into observable conditions; it cannot be a single unexplained `PASS` label or a claim that screenshots are identical.

## Outcome → Product → Presentation

The zero normalized outcome-product relationships are an architectural lead. They do not prove product meaning is absent from the source estate. The original census inspected selected normalized relationships, not every possible source declaration or extraction mapping.

There are three cases to distinguish before designing a change:

1. A product relationship is already declared but not normalized. The gap belongs in extraction or mapping.
2. An outcome identifies a product without a precise machine-readable relationship. The gap belongs in source authoring and binding.
3. A result is legitimately a scalar, a disposition, or another value that needs no artifact product identity. A presentation profile may already be sufficient.

A richer declared chain could bind a report product to its artifact contract, an authorized resource resolver, and a document presentation role. The UI would then render an appropriate preview/download through compatible providers. It would not infer a download action because a string happens to be named `artifactPath`.

This chain is a later integration opportunity rather than a prerequisite for the first profile-driven proof. It also connects output experience to subsequent workflows: a declared product may satisfy a downstream scenario input only under the relevant contract compatibility and invocation authority.

## The first proof and the evidence it must produce

The eight examples in the review remain a good primary corpus. These are evaluation subjects; listing them does not assert that all are currently prepared or runnable through one embodiment path. The earlier scaffold hold remains a historical finding, and current preparation status must be checked when implementation begins.

| Scenario | What it exercises |
|---|---|
| `greet-by-name` | Human scalar field inside an envelope; exact serialized input; simple result |
| `say-hello-world` | No editable payload values; action-only interaction |
| `resolve-sidefx-eligible-providers` | Requested target, system-bound inventory, nested collections, eligibility reasons |
| `generate-executable-capability-scaffold` | Composed root, open structures, advanced authoring, partial/held outcomes |
| `bind-external-credential-reference` | Reference selection, context binding, opaque result, sensitivity |
| `observe-governed-http-exchange` | Provider/request context and transport evidence distinct from domain success |
| `read-authorized-file` | Artifact acquisition, composed outcome, empty/missing/denied states |
| `generate-governed-narration` | Media outcome, resource resolution, findings, and lineage |

Add `validate-semantic-carrier`, whose `semantic-carrier-source.v1` input has a genuine string root. The eight original examples exercise scalar fields but should not be described as proving scalar-root support. Add adversarial fixtures for absent/null/empty/false/zero states, union overlap, reference siblings, conflicting IDs, extra members, unconstrained items, invalid draft text, and unauthorized field assignment.

The proof should produce a plan and coverage record per subject, observed target interactions, exact submitted documents, contract-admission comparisons, result interpretation evidence, and explicit unsupported findings. Pure rendering tests can use retained fixture outcomes. Live effects and provider credentials belong to separately authorized execution tests; rendering a credential selector does not require resolving a secret.

The gates are sequential:

| Gate | What becomes justified |
|---|---|
| Scoped resolution and semantic planning | The selected authority has a reproducible, complete or explicitly held plan |
| One-target interaction proof | The declared corpus behaves faithfully on the first target |
| Independently observed second target | Bounded cross-target parity for named obligations |
| Reuse and authoring evaluation | Measured evidence that the approach reduces repeated design/implementation work |

Passing these gates permits progressively stronger product claims. Failure should identify a gap in authority, compiler interpretation, provider support, or observation coverage. It should not be hidden by a generic success disposition.

## Decisions to carry forward

The recommended working direction is to retain the four layers, make the experience plan explicit and content-addressed, preserve input/outcome ownership and interpretation separately, resolve schemas within admitted scopes, and use existing presentation responsibilities wherever they fit. Missing roles, unsupported semantics, and unavailable observations should remain named findings.

Keep three maturity levels in the product language: **structural inspection**, **deterministic interaction**, and **designed experience**. The first supplies honest access to structure. The second preserves declared behavior. The third adds intentional, reusable design meaning. The evidence required for each level should remain visible.

AI-assisted authoring can propose roles, labels, profiles, and visual assets. Reviewed, retained versions can then feed deterministic compilation. Reusing that meaning removes repeated inference for the same authority; it does not eliminate design review, versioning, or the need to measure usability.

The next concrete engineering decision is a bounded design for the semantic plan and its relationship to existing UI/realization authority. The first implementation should follow the corpus above. Adding a new core database object, claiming support for every target named in the review, or declaring universal automatic UX is not established by this documentation.

The team can accurately say today:

> Research across 824 SideFX scenarios identifies a concrete path to deterministic input interactions and outcome views. Existing presentation and assurance declarations support that architecture; the experience compiler and its target conformance still need a bounded implementation proof.

The longer-term product claim, once demonstrated, is:

> A capability can carry the authority needed for its execution and human interaction, and SideFX can realize that meaning through compatible providers with evidence of preservation.
